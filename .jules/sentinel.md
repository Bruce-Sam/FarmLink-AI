## 2024-05-24 - [CRITICAL] Guarded State Transitions (TOCTOU)
**Vulnerability:** A Time-of-Check to Time-of-Use (TOCTOU) vulnerability was found in the offer state transitions (`cancelOffer`, `rejectOffer`). The application read an offer to check if it was `PENDING`, and then later performed a blind `update` on the offer status. Concurrently, `acceptOffer` could successfully mark it as `ACCEPTED` and create a transaction, locking inventory. The blind update would then overwrite the status to `CANCELLED` or `REJECTED`, permanently locking inventory and orphaning the transaction.
**Learning:** Checking state before mutation is not enough in concurrent environments. If the state machine enforces terminal states or exclusive transitions, the update itself must be guarded to ensure atomicity.
**Prevention:** Always use `updateMany` with a `status` guard (e.g., `where: { id, status: EXPECTED_STATUS }`) when mutating state variables in a concurrent environment, checking `result.count > 0` before proceeding.

## 2024-05-24 - [CRITICAL] Inventory Over-Reservation Race Condition (ACCEPT ↔ ACCEPT)
**Vulnerability:** A race condition existed where a farmer could accept two different offers for the same listing concurrently. Both transactions could read the same initial `reservedQuantity`, independently determine there was sufficient inventory available, and then perform a blind `update` on the listing to reserve the quantity. This read-modify-write race would cause the final `reservedQuantity` to be incorrect, over-allocating inventory and creating conflicting transactions.
**Learning:** Checking inventory capacity before modification in an application-level transaction is susceptible to race conditions. The actual mutation in the database must enforce the invariant.
**Prevention:** Use an optimistic concurrency control strategy when updating state derived from previously read values (e.g., `updateMany({ where: { id, reservedQuantity: expectedQuantity } })`) to ensure the state hasn't changed since it was checked.
